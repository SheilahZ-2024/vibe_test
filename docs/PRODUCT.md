# PRODUCT CONSTITUTION

## 项目名称

抖音生活服务 AI履约服务管家（Demo）

## 一、最重要原则

本项目不是：

- 智能客服
- AI问答机器人
- FAQ系统
- 帮助中心

本项目是：

**AI履约服务管家**

核心目标：

**帮助用户成功完成一次生活服务消费履约。**

衡量标准不是 AI 回答是否正确，而是用户问题是否被解决。

## 二、产品核心价值

### 用户价值

- 降低查找成本、理解成本、处理成本。
- 提升履约成功率、服务体验、问题解决效率。

### 商家价值

- 降低重复咨询、履约失败、差评风险。
- 提升到店率、核销率、用户满意度。

### 平台价值

- 提升 GMV、核销率、用户留存、商家留存。

## 三、Demo 边界

本项目是 P0 Demo。

不实现复杂 Agent 系统、多 Agent 协同、长期记忆、复杂 RAG 或复杂工作流引擎。

只验证一件事：

**AI 是否能够成为生活服务场景中的第一服务入口。**

## 四、用户旅程

所有页面设计围绕以下旅程：

```text
发现团购 → 购买订单 → 预约 → 到店 → 核销 → 售后
```

订单、优惠券、退款、工单只是系统对象，不是产品主体。

## 五、AI 出现时机

AI 不作为独立聊天机器人出现，而是嵌入履约旅程：

- 用户购买团购券：展示订单卡片、券状态、履约建议。
- 用户即将到期：展示提醒、推荐预约。
- 用户到店：展示快捷核销、门店信息。
- 核销失败：自动诊断、给出解决方案。
- 售后：解释规则、办理退款、转人工。

## 六、Agent 能力定义

Agent 职责：

```text
Understand → Observe → Diagnose → Execute → Explain
```

Agent 必须能够：

- 查询
- 解释
- 办理
- 转人工

Agent 不能只是回复文本，每次回复尽量带行动能力，例如：

- 查看订单
- 查看券码
- 重新生成核销码
- 联系商家
- 申请退款
- 转人工

## 七、Tool Calling 原则

所有业务能力必须通过 Tool 实现，禁止把业务逻辑写死在 Prompt 中。

P0 Demo 必须具备：

- `query_order`
- `query_voucher`
- `query_coupon`
- `query_store`
- `query_refund`
- `create_refund_case`
- `create_service_ticket`
- `transfer_to_human`

所有 Tool 调用结果必须可视化，用户能够看到 AI 做了什么。

## 八、UI 设计原则

整体参考：

- 抖音生活服务
- 支付宝服务助手
- Agent 化产品体验

避免纯聊天界面。

首页必须具备：

- 最近订单
- 待核销券
- 售后进度
- 推荐服务
- 履约旅程
- AI 行动区

聊天只是能力之一，不是产品主体。

## 九、必须实现的 Demo 故事

Demo 评审必须能够完整演示：

```text
用户购买火锅套餐
↓
查看订单
↓
查看券码
↓
到店消费
↓
核销失败
↓
AI自动诊断
↓
给出解决方案
↓
问题解决
↓
消费完成
```

所有功能围绕这个故事构建。
