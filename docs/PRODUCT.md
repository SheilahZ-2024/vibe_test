# 产品定义

## 项目名称

**抖音生活服务 AI 履约服务管家**（P0 Demo）

---

## 一、产品定位

### 1.1 我们是什么

**AI 履约服务管家** —— 嵌入用户履约旅程，帮用户把一次生活服务消费**做完、做好**。

| 我们**是** | 我们**不是** |
|-----------|-------------|
| 履约旅程中的第一服务入口 | 独立 FAQ 问答机器人 |
| 能查、能解释、能办理的智能助手 | 只会聊天的通用大模型 |
| 基于客观事实 + 规则推理的服务管家 | 靠 Prompt 硬编码结论的客服脚本 |

### 1.2 成功标准

**用户问题是否被解决** —— 不是模型回答是否漂亮、不是回复字数多少。

具体可观测指标（Demo 阶段）：

| 维度 | 好的表现 | 差的表现 |
|------|----------|----------|
| **准确性** | 结论与 DB 事实、券面规则一致 | 编造预约要求、错判能否核销 |
| **可执行性** | 给出下一步动作（查券/预约/退款/转人工） | 只有空洞安慰 |
| **可解释性** | 思考区展示推理过程，用户理解「为什么」 | 黑盒直接给结论 |
| **办理闭环** | 写操作有确认、有记录、有进度可查 | 口头答应但无法办理 |

## 二、核心价值

| 对象 | 价值 |
|------|------|
| **用户（C 端）** | 降低查单/理解规则/处理异常的成本；提升履约成功率与体验 |
| **商家（B 端）** | 减少重复咨询与履约失败；提升到店率与核销率 |
| **平台** | 提升 GMV、核销率、用户与商家留存；降低人工客服压力 |

## 三、用户旅程

生活服务一次消费的完整链路：

```text
发现团购 → 购买订单 → 预约（若需要）→ 到店 → 核销 → 售后/评价
              ↑           ↑              ↑       ↑        ↑
           AI 可介入    AI 可介入      AI 可介入  AI 可介入  AI 可介入
```

**AI 嵌入节点**：

| 节点 | 用户可能的问题 | 管家应能做什么 |
|------|---------------|---------------|
| 购后 | 「券在哪」「怎么用」 | 查券码、解释 usage_rule |
| 预约前 | 「要不要预约」「怎么约」 | 查门店策略、创建预约 |
| 到店前 | 「店还开着吗」「搬去哪了」 | 查 POI 状态、给新地址 |
| 核销时 | 「扫不出来」「老板不给用」 | 诊断原因、重生成码、联系商家 |
| 售后 | 「我要退款」「退到哪了」 | 查可退性、提交退款、查进度 |
| 异常 | 「吃坏肚子」「和宣传不一样」 | 安全升级、转人工、建工单 |

## 四、Agent 能力闭环

管家每次服务应走完完整闭环：

```text
Understand 理解    → 用户真正想要什么？焦点是哪笔订单？
Observe   观察    → 调工具读 DB 事实，不猜测
Diagnose  诊断    → 规则 + 诊断引擎推导 Case
Execute   执行    → 办理动作（预约/退款/转人工），写操作需确认
Explain   解释    → 用用户听得懂的话说明结论与下一步
```

对应技术实现：

| 闭环阶段 | 技术模块 |
|----------|----------|
| Understand | TurnPlanner（意图 + 接话模式） |
| Observe | BoundedGatherReAct（工具调用） |
| Diagnose | run_diagnosis → DiagnosisEngine |
| Execute | 写操作工具 + ActionSheet 确认 + workflow/actions |
| Explain | DecisionComposer（成稿）+ thinking_token（推理展示） |

### 4.1 每次回复应附带的能力

Compose 输出的 `suggested_actions` 应尽量包含可执行选项：

| 能力 | 典型 action |
|------|-------------|
| 查订单 | 已在 Gather 完成，回复中引用 |
| 查券码 | 同上 |
| 重新生成核销码 | regenerate_qr |
| 联系商家 | contact_merchant |
| 创建预约 | create_reservation |
| 申请退款 | apply_refund |
| 转人工 | human_handoff |

工具调用过程对用户**可见**（思考流 + 操作记录面板）。

## 五、Tool Calling 原则

### 5.1 为什么用 Tool

业务能力通过 **Tool（工具）** 实现，而不是 Prompt 硬编码：

| 原则 | 说明 |
|------|------|
| **事实来自 DB** | 订单状态、券规则、门店信息必须从工具返回 |
| **结论来自推理** | 跨店、缺预约等由诊断引擎 + Compose 推理 |
| **写操作需确认** | 退款/预约等不可逆操作必须用户点确认 |
| **Gather 只读** | 核实阶段禁止写；办理在确认后进行 |

### 5.2 工具分层

```text
只读工具（Gather 阶段）
  list_orders / query_focus_bundle / query_* / search_knowledge / run_diagnosis

写操作工具（需 user_confirmed 或 ActionSheet）
  regenerate_qr / contact_merchant / create_reservation / apply_refund / human_handoff
```

### 5.3 模型主导 vs 程序约束

| 谁决定 | 什么 |
|--------|------|
| **大模型（Gather ReAct）** | 查什么规则、调哪些工具、何时结束 Gather |
| **大模型（Compose）** | 如何向用户解释、建议什么动作 |
| **程序（fact_sheet）** | 结构化事实抽取，防编造 |
| **程序（Verify）** | 嵌在 Compose 模块内：预约硬约束等不可违反的规则 |
| **用户（ActionSheet）** | 写操作最终确认 |

## 六、统一 Pipeline 产品视角

从技术视角，每轮对话走 **Plan → Gather → fact_sheet → Compose（内含 Verify）→ Emit**：

```text
┌─────────────────────────────────────────────────────────────┐
│ Plan 规划                                                    │
│   识别意图：「没预约能核销吗」→ CheckVoucherAvailability       │
│   接话模式：新话题 / 续问 / 致谢                              │
├─────────────────────────────────────────────────────────────┤
│ Gather 核实（用户看到思考区灰字）                             │
│   模型决定：先查 focus_bundle，再 run_diagnosis → SDS         │
│   核对规则：「须提前预约」「订单无预约记录」                    │
│   SDS/工具 observation 回写 Gather 下一步 LLM                │
├─────────────────────────────────────────────────────────────┤
│ fact_sheet 事实表（程序，用户无感知）                         │
│   汇总查库 + usage_rules + SDS Case 标签；非 LLM 推理摘要      │
├─────────────────────────────────────────────────────────────┤
│ Compose 成稿（用户看到正式回复）                              │
│   单次 LLM：读 trace + fact_sheet + 诊断块 → 写 reply        │
│   内部 Verify：拦截「须预约却说可直接核销」等，失败则重写       │
├─────────────────────────────────────────────────────────────┤
│ Emit 输出                                                    │
│   流式推送正式回复；可选语气润色                               │
└─────────────────────────────────────────────────────────────┘
```

**与旧架构的区别**（产品侧）：

| 旧版 | 现行 |
|------|------|
| 多轮 ReAct 边想边说 | Gather 有界 3 步 + Compose 单次成稿 |
| 独立润色 LLM | 默认 Compose 直接输出；润色可选 |
| 快慢双轨 | 统一单管线 |
| 思考区套话 | 透传模型真实 thought |

## 七、UI 原则

参考「**会话即服务（Conversation as a Service）**」：

### 7.1 信息架构

```text
主界面（ConversationView）
  ├── 焦点订单条 — 当前在处理哪一笔
  ├── 消息流 — 用户输入 + 管家回复
  ├── 思考区 — 灰字推理（observing 阶段）
  ├── 服务卡片 — 订单/券/门店摘要
  ├── 动作按钮 — suggested_actions
  └── 输入框 + 快捷话术

+ 半屏（BottomSheet）
  ├── 服务进度 — 购买→预约→到店→核销→售后 时间线
  ├── 历史订单 — 全部订单列表
  ├── 操作记录 — 退款金额、到账状态、工具调用
  └── 授权设置 — 隐私开关（位置/订单/券/行为摘要）
```

### 7.2 交互原则

| 原则 | 实现 |
|------|------|
| **聊天是载体，不是全部** | 进度、记录、办理与对话同等重要 |
| **思考可见** | 用户能看到管家在核实什么，建立信任 |
| **内部术语不可见** | Case 编号、Intent 代码、工具英文名不展示 |
| **写操作可撤销感** | ActionSheet 二次确认，操作记录可追溯 |
| **Demo 可切换** | 120 用户一键切换，覆盖正常与异常 |
| **实时时钟** | 状态栏显示本机时间，规则判断与之对齐 |

### 7.3 流式体验阶段

| 阶段 | streamPhase | 用户看到 |
|------|-------------|----------|
| 思考中 | `observing` | ThinkingStream 灰字逐字出现 |
| 回复中 | `replying` | 正式气泡流式输出；思考区缩小 |
| 完成 | — | 动作按钮出现；可继续输入 |

## 十、数据原则（产品 + 技术共识）

### 10.1 库中只存事实

Mock 数据写入的是**可观测业务事实**：

```text
✅ 订单状态 unused/scheduled/used/expired/refunding/refunded
✅ 券 usage_rule 原文（「须提前预约」「仅限周末」）
✅ 门店 supports_reservation / business_status / 营业时间
✅ 履约事件、退款单记录

❌ 诊断 Case 标签（如「此用户是 PC-010」）
❌ 预置结论（如「此单不可核销」）
```

### 10.2 诊断在运行时推导

用户说「没预约能核销吗」+ user_096 的数据事实 → 引擎推导 PC-010 → Compose 向用户解释。

这保证了 Demo **长期可玩**：换话术、换时间、换用户，结论随事实变化。
