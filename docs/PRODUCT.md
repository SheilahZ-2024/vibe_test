# PRODUCT CONSTITUTION

## 项目名称

抖音生活服务 AI履约服务管家（Demo）

## 一、最重要原则

本项目不是：

- 智能客服
- AI问答机器人
- FAQ系统
- 帮助中心

本项目是：

**AI履约服务管家**

核心目标：

**帮助用户成功完成一次生活服务消费履约。**

衡量标准不是 AI 回答是否正确，而是用户问题是否被解决。

## 二、产品核心价值

### 用户价值

- 降低查找成本、理解成本、处理成本。
- 提升履约成功率、服务体验、问题解决效率。

### 商家价值

- 降低重复咨询、履约失败、差评风险。
- 提升到店率、核销率、用户满意度。

### 平台价值

- 提升 GMV、核销率、用户留存、商家留存。

## 三、Demo 边界

本项目是 P0 Demo。

不实现复杂 Agent 系统、多 Agent 协同、长期记忆、复杂 RAG 或复杂工作流引擎。

只验证一件事：

**AI 是否能够成为生活服务场景中的第一服务入口。**

## 四、用户旅程

所有页面设计围绕以下旅程：

```text
发现团购 → 购买订单 → 预约 → 到店 → 核销 → 售后
```

订单、优惠券、退款、工单只是系统对象，不是产品主体。

## 五、AI 出现时机

AI 不作为独立聊天机器人出现，而是嵌入履约旅程：

- 用户购买团购券：展示订单卡片、券状态、履约建议。
- 用户即将到期：展示提醒、推荐预约。
- 用户到店：展示快捷核销、门店信息。
- 核销失败：自动诊断、给出解决方案。
- 售后：解释规则、办理退款、转人工。

## 六、Agent 能力定义

Agent 职责：

```text
Understand → Observe → Diagnose → Execute → Explain
```

Agent 必须能够：

- 查询
- 解释
- 办理
- 转人工

Agent 不能只是回复文本，每次回复尽量带行动能力，例如：

- 查看订单
- 查看券码
- 重新生成核销码
- 联系商家
- 申请退款
- 转人工

## 七、Tool Calling 原则

所有业务能力必须通过 Tool 实现，禁止把业务逻辑写死在 Prompt 中。

P0 Demo 必须具备：

- `query_order`
- `query_voucher`
- `query_coupon`
- `query_store`
- `query_refund`
- `create_refund_case`
- `create_service_ticket`
- `transfer_to_human`

所有 Tool 调用结果必须可视化，用户能够看到 AI 做了什么。

## 八、UI 设计原则（当前 Demo）

整体参考抖音生活服务、支付宝服务助手——**会话即服务**，而非纯聊天。

当前实现：

- **主界面**：全屏会话 + 焦点订单摘要 + 流式思考 + 服务卡片
- **+ 半屏**：服务进度时间线、历史订单、操作记录、授权设置
- **用户切换**：120 mock 用户，覆盖正常履约与异常场景
- **状态栏**：实时本机时钟，强化「在线 Demo」感

聊天是载体；进度、记录、办理动作与对话同等重要。

## 九、体验场景（非单一故事线）

Demo 不绑定「火锅套餐」等固定剧本，而是 **120 用户 × 多意图** 的组合体验：

| 场景类型 | 体验方式 |
|----------|----------|
| 查单/查券 | 任意正常用户 + 「查看券码」「订单到哪了」 |
| 核销失败 | user_081+ 异常用户 + 「扫不出来」「老板说不认券」 |
| 门店/预约 | 「店关门了」「约不上」 |
| 售后退款 | 「我要退款」+ 操作记录里看退款进度 |
| 安全投诉 | 「吃坏肚子」→ P0 Case |

所有能力围绕 **Understand → Observe → Diagnose → Execute → Explain** 闭环验证，而非一条线性火锅故事。
